Проект: TraceForge
Версия: 1.0
Дата: 13.10.2026

1. ОБЩЕЕ ОПИСАНИЕ

TraceForge — веб-приложение для сбора, хранения, поиска и анализа событий выполнения распределённых приложений. Система должна помогать разработчикам исследовать цепочки событий по traceId, видеть последовательность действий между сервисами, выявлять ошибки и безопасно повторять отдельные HTTP-запросы в контролируемой тестовой среде.

Проект предназначен для изучения Java и Spring Boot на примере системы, приближенной к production-проекту. При этом архитектура и код должны быть достаточно простыми для последовательного освоения, без преждевременного усложнения.

Основная идея: пользователь отправляет события в TraceForge через REST API, система сохраняет их в PostgreSQL, а пользователь через веб-интерфейс ищет события, открывает трассировку и анализирует последовательность выполнения.

5. ОСНОВНЫЕ ПОНЯТИЯ И МОДЕЛЬ ДАННЫХ

5.1. TraceEvent

Одна запись о событии, произошедшем в приложении или сервисе.

Предлагаемые поля:
- id: UUID — уникальный идентификатор события.
- traceId: String — идентификатор трассировки, обязательный.
- serviceName: String — имя сервиса, обязательное.
- eventType: String или enum — тип события, обязательный.
- message: String — краткое описание события, обязательное.
- severity: enum — INFO, WARN, ERROR; по умолчанию INFO.
- occurredAt: Instant — время возникновения события.
- receivedAt: Instant — время приёма события TraceForge.
- durationMs: Long — длительность события, необязательное неотрицательное значение.
- metadata: JSON/JSONB — необязательные дополнительные атрибуты.
- correlationId: String — необязательный идентификатор корреляции.
- errorCode: String — необязательный код ошибки.
- errorDetails: String — необязательные подробности ошибки.

Для MVP не следует добавлять поля, которые не используются в API или интерфейсе. Типы и обязательность полей нужно согласовать с фактической схемой DTO и миграциями.

5.2. Trace

Trace — логическая группа событий с одинаковым traceId. На первом этапе отдельная таблица Trace не обязательна: трассировка может формироваться запросом к TraceEvent. Если позднее появятся собственные атрибуты трассировки или требования к производительности, модель можно расширить.

5.3. Идентификаторы и время

- Время хранить в UTC.
- API должен использовать ISO 8601 для временных значений.
- traceId должен иметь ограничение по длине и проходить валидацию.
- Для сортировки использовать occurredAt и стабильный дополнительный ключ, например id.
- Нужно явно определить поведение при повторной отправке одного события. Идемпотентность можно реализовать отдельным этапом.

6. REST API

Базовый префикс: /api.

6.1. Приём события

POST /api/events

Принимает JSON с данными события. Проверяет обязательные поля и ограничения, присваивает id и receivedAt, сохраняет запись в БД и возвращает созданное событие либо подтверждение приёма.

Пример запроса:
{
  "traceId": "trace-123",
  "serviceName": "payment-service",
  "eventType": "PAYMENT_CREATED",
  "message": "Payment request received",
  "severity": "INFO",
  "occurredAt": "2026-10-13T12:00:00Z",
  "durationMs": 125,
  "metadata": {
    "paymentId": "pay-456"
  }
}

Это пример контракта, а не требование добавлять каждое поле в первую реализацию. Фактический DTO должен соответствовать модели данных и возможностям текущего проекта.

6.2. Получение события

GET /api/events/{id}

Возвращает событие по UUID. Если событие не найдено, API должен возвращать HTTP 404 с единым форматом ошибки.

6.3. Поиск событий

GET /api/events

Поддерживаемые query-параметры:
- traceId — точное совпадение.
- serviceName — фильтр по сервису.
- eventType — фильтр по типу.
- severity — фильтр по уровню.
- from — начало временного диапазона.
- to — конец временного диапазона.
- page — номер страницы, начиная с 0.
- size — размер страницы с ограничением максимального значения.
- sort — разрешённое поле сортировки и направление.

Ответ должен содержать элементы текущей страницы и метаданные пагинации. Не возвращать весь набор событий без ограничений.

6.4. Просмотр трассировки

GET /api/traces/{traceId}

Возвращает события с указанным traceId в хронологическом порядке. При необходимости ответ может включать сводную информацию: количество событий, число ошибок, список задействованных сервисов и временной диапазон. Для MVP достаточно корректной хронологии и базовых метаданных.

6.5. Проверка состояния

GET /actuator/health

Использовать Spring Boot Actuator. Не раскрывать через публичные endpoints чувствительную конфигурацию, секреты или внутренние данные.

7. ВАЛИДАЦИЯ И ОБРАБОТКА ОШИБОК

- Использовать Jakarta Bean Validation на входных DTO.
- Контроллеры не должны содержать бизнес-логику и код прямой работы с SQL.
- Ошибки обрабатывать централизованно через общий обработчик исключений.
- Возвращать корректные HTTP-коды: 400 для некорректного запроса, 404 для отсутствующей записи, 409 для конфликтов при наличии такого сценария, 500 для непредвиденных ошибок.
- Формат ошибки должен быть единым и включать timestamp, status, error/code, message и path; детали валидации при необходимости возвращать отдельным списком.
- Не отправлять stack trace, SQL, пароли и внутренние технические детали клиенту.
- Не проглатывать исключения без логирования и корректного ответа.

8. АРХИТЕКТУРА BACKEND

Использовать модульный монолит с разделением ответственности:

- controller — HTTP-контракты и преобразование запросов/ответов.
- dto — входные и выходные модели API.
- service — бизнес-логика.
- repository — доступ к данным через Spring Data JPA.
- entity — сущности хранения.
- exception — прикладные исключения и единая обработка ошибок.
- config — конфигурация приложения.
- mapper — преобразование entity и DTO, если оно становится достаточно сложным.

Не возвращать JPA entity напрямую из публичного API. Не размещать бизнес-логику в контроллерах. Не создавать абстракции, интерфейсы и фабрики без реальной необходимости.

Сначала изучить существующую структуру проекта и продолжать в её стиле, если он не противоречит этому ТЗ.

9. БАЗА ДАННЫХ И МИГРАЦИИ

- Использовать PostgreSQL.
- Все изменения схемы выполнять через версионируемые миграции Flyway.
- Не полагаться на автоматическое создание production-схемы через Hibernate ddl-auto.
- Добавить индексы для traceId, occurredAt и полей, реально участвующих в фильтрации.
- Продумать индексы с учётом наиболее частых запросов, не создавая индекс на каждое поле без необходимости.
- Настроить ограничения для обязательных полей и разумные длины строк.
- Убедиться, что временные поля и часовые пояса обрабатываются предсказуемо.
- Проверить миграции на чистой БД и на БД, содержащей предыдущую версию схемы.

10. FRONTEND

Разработать интерфейс на Next.js, React и TypeScript.

Основные страницы:
- Главная/Overview: краткая сводка событий и ошибок, если доступна необходимая статистика.
- Events: таблица событий с фильтрами, сортировкой и пагинацией.
- Trace Details: события одной трассировки в хронологическом порядке.
- Event Details: подробная информация о выбранном событии.

Требования:
- Ясные состояния загрузки, пустого результата и ошибки.
- Фильтры должны отражаться в URL, если это уместно для повторного открытия и обмена ссылками.
- Длинные сообщения и metadata должны отображаться читаемо.
- ERROR и WARN должны визуально различаться, но цвет не должен быть единственным способом передачи значения.
- Интерфейс должен оставаться удобным на типовых desktop-экранах и адаптироваться к узким экранам.
- Не обращаться к PostgreSQL напрямую из frontend.
- Адрес backend должен задаваться конфигурацией окружения.
- Не добавлять фиктивные данные в production-сценарии; mock-данные допустимы только для разработки и тестов.

12. SAFE REPLAY ENGINE — ПОСЛЕДУЮЩИЙ ЭТАП

Назначение: безопасно повторить сохранённый HTTP-запрос в контролируемой тестовой среде и сравнить результат с исходным.

Replay Engine не входит в минимальный этап приёма и просмотра событий. Его нужно проектировать и реализовывать после готовности основной модели данных, API и тестов.

Требования безопасности:
- Разрешать запросы только к заранее настроенным allowlist-хостам.
- Запрещать loopback, private, link-local и metadata IP-адреса, если они не разрешены явно для изолированной локальной среды.
- Не позволять клиенту передавать произвольный target URL без проверки.
- Запускать повторы только в явно выбранной тестовой среде.
- Устанавливать таймауты, лимиты размера запроса/ответа и ограничения частоты.
- Не пересылать Authorization, Cookie и другие секретные заголовки автоматически.
- Не выполнять операции, которые могут привести к реальному списанию денег, изменению production-данных или другим необратимым последствиям.
- Хранить результат повтора отдельно от исходного события.
- Записывать время, target, статус, длительность и безопасно очищенное сравнение результатов.
- Ошибки и сетевые таймауты должны отображаться как результаты выполнения, а не приводить к падению всего приложения.

13. ТЕСТИРОВАНИЕ

Unit-тесты:
- валидация и бизнес-правила сервиса;
- корректная обработка отсутствующих событий;
- расчёт и сортировка данных, если применимо;
- преобразование ошибок.

Web/integration-тесты:
- POST /api/events: успешный запрос и ошибки валидации;
- GET /api/events/{id}: найдено/не найдено;
- GET /api/events: фильтрация и пагинация;
- GET /api/traces/{traceId}: порядок событий;
- корректные HTTP-коды и единый формат ошибок;
- работа миграций и репозиториев с PostgreSQL.

По мере развития проекта использовать Testcontainers для тестов с настоящим PostgreSQL. Тесты не должны зависеть от порядка выполнения и не должны требовать вручную подготовленной локальной БД.

14. ЛОГИРОВАНИЕ И НАБЛЮДАЕМОСТЬ

- Использовать структурированные и понятные логи.

18. КРИТЕРИИ ПРИЁМКИ MVP

MVP считается готовым, если:
1. Backend запускается по документации на чистом окружении.
2. POST /api/events валидирует запрос и сохраняет событие в PostgreSQL.
3. Некорректный запрос возвращает HTTP 400 в едином формате ошибки.
4. Событие можно получить по id.
5. События можно искать по traceId и доступным фильтрам.
6. Пагинация ограничивает размер выдачи.
7. GET /api/traces/{traceId} возвращает события в стабильном хронологическом порядке.
8. Frontend позволяет искать события и открывать трассировку.
9. Данные не теряются при перезапуске контейнера PostgreSQL.
10. Миграции Flyway применяются на чистой БД.
11. Основные сценарии покрыты автоматическими тестами.

19. ТРЕБОВАНИЯ К РАБОТЕ С AI-КОДИНГ-АГЕНТАМИ

При использовании AI-агента:
- Перед изменениями изучать существующий код, структуру проекта, pom.xml, миграции и тесты.
- Не переписывать проект целиком без необходимости.
- Не менять стек и версии зависимостей без объяснения причины и проверки совместимости.
- Реализовывать требования небольшими логически завершёнными частями.
- После каждого этапа запускать тесты и сборку.
- Не утверждать, что задача выполнена, если проверки не запускались или завершились ошибкой.
- Не подменять реальную интеграцию mock-данными.
- Не добавлять неописанные endpoint'ы и сущности без обоснования.
- При неоднозначном требовании сначала фиксировать предположение и его последствия.
- Сохранять обратную совместимость существующих API, если изменение контракта явно не согласовано.
- В конце этапа сообщать: какие файлы изменены, что реализовано, какие команды проверки выполнены, результаты проверок и какие ограничения остались.
